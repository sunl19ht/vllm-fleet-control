## 1. 项目目标与第一版成功标准

### 1.1 一句话定位

vLLM Fleet Control 是面向运维人员的 vLLM 推理集群管理控制台，用于管理 Router、Host 和推理实例，查看健康与监控数据，并追踪受控的实例生命周期操作。

推理请求由现有 Router 转发给 vLLM Worker，管理平台不承载推理流量。

### 1.2 第一版要完成的用户闭环

1. 管理员登录管理平台。
2. 登记 Router、主机和已有推理实例，建立资源之间的关联。
3. 平台检查实例健康，显示最后探测时间、结果和错误原因。
4. 管理员查看 Prometheus 提供的监控数据；无数据时获得明确提示。
5. 对已配置且授权管理的 systemd 实例提交启动、停止或重启任务。
6. 在任务详情中查看阶段、执行结果、耗时与审计记录。
7. 其他开发者按 README 在一套测试环境中完成上述流程。

### 1.3 什么算 v0.1.0 完成

- 工程可从干净仓库启动，数据库迁移可重复执行而不会重复建表。
- Router、Host、Instance 的登记、查询、修改和受约束删除可用。
- 实例状态来自真实探测，失败、未知和过期状态可区分。
- 至少一套测试环境完成真实 vLLM 与 Prometheus 联调。
- systemd 生命周期任务具备权限检查、目标约束、超时、并发互斥和审计。
- 关键异常场景通过测试，部署、配置、限制与恢复方式写入文档。
- 发布包不包含凭据、私钥、真实环境地址等敏感配置。

## 3. v0.1 功能范围与边界

### 3.1 本版必须实现

| 模块 | 最小功能 | 验收要点 |
| --- | --- | --- |
| 登录与权限 | 单管理员登录、会话失效、接口鉴权 | 未登录不能查询资源或提交操作 |
| Router 管理 | 登记名称、地址、备注及适配配置 | 地址经过校验；展示已配置和已验证能力 |
| Host 管理 | 登记主机、SSH 用户及凭据引用 | 查询响应不泄露凭据 |
| Instance 管理 | 关联 Router、参与主机和服务单元 | 不把数据库登记状态当成运行状态 |
| 健康探测 | 真实 HTTP 探测、超时和结构化错误 | 失败原因、时间和数据新鲜度可见 |
| 监控 | 查询已配置 Prometheus 并展示少量核心指标 | 能区分零值、无数据和查询失败 |
| 生命周期任务 | 支持已授权 systemd 服务的单实例操作 | 任务可追踪，重复点击受控 |
| 审计与部署 | 记录操作人、目标、结果；提供部署指南 | 新环境可按文档复现 |

### 3.2 本版暂不承诺

- 自动发现所有 Router Worker，或兼容任意 Router 实现与版本。
- 多节点实例的自动编排、无中断升级或滚动重启。
- 新建推理部署、自动安装驱动、自动下载模型。
- Kubernetes Operator、主机 Agent、多租户计费和完整 RBAC。
- 自建推理网关或让推理流量经过管理后端。
- 同时完成 systemd、Podman、Docker、Kubernetes 的全部适配。

多主机参与关系可以登记；v0.1 的可操作目标限定为经过验证的单一服务单元。超出该范围的实例显示为只读，不能伪装成已具备编排能力。

### 3.3 范围变更规则

新增需求先进入 Backlog。只有阻碍当前用户闭环或修复安全、数据正确性问题的内容，才进入当前里程碑。其他需求在 v0.1.0 发布后重新排序。

## 5. 系统架构与核心资源

### 5.1 三条链路

```text
管理链路：管理员 → Vue 控制台 → Spring Boot → PostgreSQL
                                      ├→ Router / vLLM HTTP API
                                      ├→ Prometheus HTTP API
                                      └→ 受限 SSH → systemd

推理链路：业务客户端 → 已有 Router → vLLM Worker

监控链路：Prometheus → 采集目标指标；管理平台 → 查询 Prometheus
```

健康探测、监控查询与生命周期命令分别处理。HTTP 健康不等于进程状态，进程运行也不等于模型已经可用。

### 5.2 核心资源

| 资源 | 含义 | 建议最小字段 |
| --- | --- | --- |
| Router | 推理入口或路由服务 | id、name、baseUrl、adapterType、备注 |
| Host | 实际计算主机 | id、name、address、sshPort、sshUser、credentialRef |
| Instance | 一个逻辑推理服务 | id、name、routerId（可选）、endpoint、runtimeType、operationMode |
| InstanceHost | 实例与参与主机的关联 | instanceId、hostId、role、serviceUnit（可选） |
| HealthSnapshot | 最近一次探测结果 | instanceId、status、checkedAt、latency、errorCode |
| Task | 一次生命周期操作 | id、instanceId、action、status、actor、时间、结果 |
| TaskEvent | 任务阶段与诊断事件 | taskId、sequence、stage、message、createdAt |
| AuditEvent | 管理操作的审计记录 | actor、action、target、requestId、result、createdAt |

表名、类型和索引在 M1 通过迁移文件确定。这里给出的是执行基线，不构成已验证的完整数据库设计。

### 5.3 状态建模原则

- 保留用户配置、运行时状态、HTTP 健康、最后更新时间四类信息。
- 健康状态最少区分 `UNKNOWN`、`HEALTHY`、`UNHEALTHY`；过期结果显示“数据已过期”。
- SSH 失败表示无法读取运行时状态，不能直接推断服务已停止。
- 健康检查失败不能直接说明是哪一块 GPU、模型或节点故障。
- 通过适配器隔离 Router、vLLM、Prometheus 和运行时差异。

目录应有实际文件支撑；Git 不保留空目录，需要时添加模块 README。数据库迁移统一放在后端资源目录，避免另建一套重复 SQL 来源。

### 6.1 开发环境完成标准

- 后端有 Maven Wrapper 或等效固定构建入口。
- 前端使用一个确定的包管理器，提交对应锁文件。
- 本地配置通过环境变量或不入库的配置文件提供。
- `.env.example` 只写变量名称和无敏感性的示例值。
- PostgreSQL 的开发数据目录、构建产物和 IDE 临时文件不会入库。
- README 明确安装前提、启动顺序、访问地址和停止方式。
- CI 至少完成后端编译与测试、前端类型检查与构建。

## 7. M0–M6 里程碑与完成门槛

以下是按原对话方向重建的七阶段计划。阶段名称和具体任务是本次补全的执行建议，按完成门槛推进，不以日历到期代替验收。

| 阶段 | 交付目标 | 关键工作 | 必须出示的验收证据 |
| --- | --- | --- | --- |
| M0 工程初始化 | 三端基础链路跑通 | 仓库、前后端、数据库、迁移、CI | 干净环境启动；前端调用真实后端 API；迁移与 CI 成功 |
| M1 资源与访问基线 | 能安全登记管理资源 | 登录鉴权；Router、Host、Instance CRUD；关系约束 | 未登录被拒；合法数据可保存；非法及关联删除受控 |
| M2 实例探测 | 显示可信健康信息 | HTTP 客户端、定时探测、超时、错误分类、状态新鲜度 | 真实 vLLM 探测；模拟超时和异常；状态正确展示 |
| M3 监控闭环 | 看见真实运行指标 | Prometheus 适配、实例标签映射、图表、空状态 | 至少一组真实指标；无数据和失败可区分 |
| M4 生命周期任务 | 安全执行单实例操作 | systemd 适配、异步任务、锁、审计、恢复处理 | 测试实例真实操作；超时、重复提交、权限失败均受控 |
| M5 集成与部署 | 形成完整用户闭环 | UI 串联、部署说明、故障处理、集成回归 | 从登录到任务完成的演示与验收记录 |
| M6 开源发布 | 发布可复现版本 | 文档、示例、许可证、发布说明、标签 | 另一套干净环境按 README 复现；发布检查完成 |

### 7.1 每个阶段的退出规则

1. 当前阶段的必做 Issue 已完成。
2. 验收记录写明环境、提交版本、步骤和结果。
3. 没有阻止数据正确性、安全操作或主流程的未解决问题。
4. 未验证项目单独列出，并决定修复还是明确缩小发布范围。
5. 更新文档与待办清单后再进入下一阶段。

### 7.2 工期使用方式

先记录第一周实际可投入时间和任务耗时，再估算剩余工期。不要把“两个人”理解成两个全天候独立执行者；开发环境操作和验证仍需要你安排时间。

## 10. 接口与数据约定

本章是接口设计草案，M1 开始前应在 `docs/API_SPEC.md` 固化。尚未实现的接口不得在 README 中标为可用。

### 10.1 建议接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET / POST | `/api/v1/routers` | 查询 / 登记 Router |
| GET / PATCH / DELETE | `/api/v1/routers/{id}` | 查看 / 修改 / 删除 Router |
| GET / POST | `/api/v1/hosts` | 查询 / 登记 Host |
| GET / PATCH / DELETE | `/api/v1/hosts/{id}` | 查看 / 修改 / 删除 Host |
| GET / POST | `/api/v1/instances` | 查询 / 登记 Instance |
| GET / PATCH / DELETE | `/api/v1/instances/{id}` | 查看 / 修改 / 删除 Instance |
| GET | `/api/v1/instances/{id}/health` | 获取最近探测结果与时间 |
| POST | `/api/v1/instances/{id}/health-checks` | 触发一次受并发限制的探测 |
| GET | `/api/v1/instances/{id}/metrics` | 查询限定指标和时间范围 |
| POST | `/api/v1/instances/{id}/tasks` | 提交 start / stop / restart 操作 |
| GET | `/api/v1/tasks/{id}` | 查询任务详情 |
| GET | `/api/v1/tasks/{id}/events` | 查询任务事件；SSE 可作为后续增强 |

登录相关路径和会话方式在认证设计时补全，避免在此草率指定存储令牌方案。

### 10.2 公共约定

- ID 类型全项目一致；客户端不要依赖连续编号。
- 时间使用带时区的 ISO 8601 表示，存储基准统一；前端按用户时区显示。
- 列表设置分页、最大页大小和明确的排序方式。
- 创建、修改操作校验必填、长度、枚举、URL 和资源关联。
- 删除存在实例关联的资源时拒绝并说明原因，不能静默级联破坏配置。
- 外部错误映射成稳定业务错误码；响应不得包含私钥、凭据或完整远程命令输出。
- 任务提交后返回任务标识；提交成功不等于执行成功。

建议错误结构：

```json
{
  "code": "INSTANCE_OPERATION_CONFLICT",
  "message": "该实例已有运行中的任务",
  "requestId": "example-request-id"
}
```

### 10.3 数据与配置

- 凭据使用引用或受保护的秘密存储；不要把 SSH 私钥和密码存进普通业务字段。
- 任务、事件和审计记录定义保留时间与清理方式。
- 状态更新具备版本或时间校验，防止较旧探测覆盖较新结果。
- 数据库约束兜底保证关联、唯一性和非空要求，不能只靠表单校验。
- 迁移在测试环境先验证；发布过的迁移通过新增文件演进。

## 11. 生命周期任务与运行时适配

### 11.1 任务状态

```text
QUEUED → RUNNING → SUCCEEDED
                → FAILED
                → TIMED_OUT
```

平台进程中断时，将过期运行任务进入待核查的 `UNKNOWN` 状态，并阻止同目标新操作，直到完成状态核对与锁处理。远程命令可能已经执行，不能把平台重启简单等同于远程操作失败，也不能自动重放非幂等操作。

v0.1 不承诺任务取消。若以后增加取消，需要区分“取消等待”和“终止远程执行”。

### 11.2 提交和执行流程

1. 鉴权并确认实例在可操作范围内。
2. 检查主机、凭据引用、已登记服务单元和允许的动作。
3. 在事务内创建任务，申请实例级互斥，并处理幂等键。
4. 后台执行器领取已提交的任务，写入开始事件。
5. 运行时适配器通过受限 SSH 执行预定义动作。
6. 在总截止时间内核对运行时与健康状态。
7. 持久化结果、事件和审计，再释放互斥。

命令超时后若无法确认远程状态，应进入待核查流程并继续阻止冲突操作。不要仅因本地等待结束就允许第二次重启。

### 11.3 不同动作的完成条件

| 动作 | 完成条件 |
| --- | --- |
| start | 服务单元运行且目标 HTTP 健康达到约定条件 |
| stop | 服务单元已停止；HTTP 不可达仅作为辅助信息 |
| restart | 重启动作执行完成，运行时及 HTTP 健康重新满足条件 |

模型加载可能需要较长时间。操作总超时应配置化，并在测试环境测量后设定，不能无限等待。

### 11.4 运行时适配边界

适配器负责查询状态和执行受控动作，任务服务负责授权、持久化、重试策略、超时与审计。适配器不自行发起无限重试。

首版只实现 systemd。Podman 等实现保留扩展位置，不创建没有验证价值的空实现。

### 11.5 操作页面要求

- 提交前显示实例、主机、服务单元及动作。
- 对停止和重启显示明确确认步骤。
- 已有活动任务时禁用冲突按钮，并给出任务入口。
- 任务页面区分等待、执行、等待健康和结束结果。
- 失败后提供脱敏原因与排查方向，不直接自动重试。

## 12. 测试矩阵与验收流程

### 12.1 必测场景

| 范围 | 场景 | 期望结果 |
| --- | --- | --- |
| 构建 | 干净环境安装依赖并构建 | 前后端检查通过，无依赖本机隐藏配置 |
| 数据库 | 空库迁移、重复启动、升级迁移 | 结构正确，历史数据保留，异常可诊断 |
| 权限 | 未登录查询或提交操作 | 请求被拒绝，不产生远程执行 |
| CRUD | 无效地址、重复记录、缺失关联 | 校验失败且提示明确 |
| 删除 | 删除仍被实例引用的资源 | 拒绝并说明关联关系 |
| 探测 | 健康、连接拒绝、超时、HTTP 500 | 正确分类；最后检查时间更新 |
| API 适配 | 无效 JSON、缺字段、不支持的接口 | 返回可理解的适配错误，不伪造能力 |
| 状态新鲜度 | 长时间无新探测、响应乱序 | 结果显示过期；旧响应不覆盖新结果 |
| 监控 | 有数据、空结果、Prometheus 不可达 | 图表分别显示数据、无数据和错误 |
| SSH | 错误主机身份、连接失败、无权限 | 拒绝或失败；凭据和命令细节不泄露 |
| 生命周期 | 测试实例 start / stop / restart | 任务结果符合对应动作的完成条件 |
| 并发 | 重复点击、相同幂等键、并发任务 | 不产生重复或冲突操作 |
| 超时 | 命令或模型加载超过截止时间 | 有终态或待核查状态，冲突操作仍受控 |
| 恢复 | 执行中重启管理平台 | 能识别遗留任务，不盲目重放 |
| 审计 | 成功、失败、拒绝的管理操作 | 操作人、目标、时间、结果可追踪 |
| 前端 | 加载、空列表、接口异常、提交中 | 状态清楚，按钮防重复，错误可恢复 |

### 12.2 测试层次

- 单元测试：状态转换、校验、错误分类和并发规则。
- 适配集成测试：使用可控 HTTP / SSH 替身模拟超时和异常，校验协议处理。
- 数据库集成测试：迁移、约束、事务及任务领取的并发行为。
- 真实环境验收：在隔离测试实例上联调 vLLM、Prometheus 与 systemd。

Mock 通过不能代替真实环境验收。执行生命周期测试前确认测试目标，避免误操作正在承担业务的实例。

### 12.3 验收记录格式

```text
里程碑 / Issue：
提交版本：
环境及依赖版本：
前置条件：
操作步骤：
预期结果：
实际结果及证据：
结论：通过 / 失败 / 未验证
遗留问题与处理决定：
验收人及日期：
```

验收记录统一放入 `docs/ACCEPTANCE.md` 或其引用的文件，附脱敏日志、截图或测试报告位置。

## 13. Git、Issue、PR 与文档规范

### 13.1 分支与提交

- `main` 保持可构建、可演示。
- 一个 Issue 使用一个短期分支，例如 `feat/instance-health`。
- 一个 PR 聚焦一个可验收结果；数据库、后端、前端可以围绕同一结果一起提交。
- 提交说明使用清晰动作，例如 `feat: add instance health probe`、`fix: reject concurrent restart tasks`。
- 不在主分支堆积没有验收的功能，不提交密码、私钥和真实配置。

### 13.2 Issue 模板

```markdown
## 目标
说明用户需要获得的结果。

## 范围
列出本次实现内容及明确边界。

## 输入与约束
现有代码、接口契约、环境、依赖任务。

## 验收标准
- [ ] 可观察、可复现的行为
- [ ] 关键异常场景
- [ ] 必要文档更新

## 验证方式
运行步骤、测试数据与预期结果。

## 交付
修改文件、PR、实际验证结果与遗留问题。
```

### 13.3 PR 模板

```markdown
## 问题与结果
描述什么场景下原来有什么问题，现在会如何表现。

## 关键改动
仅说明审查需要了解的实现与数据变化。

## 验证
已执行的检查、环境和结果；未验证项及原因。

## 部署影响
配置、迁移、兼容性与恢复方式。

关联 Issue：
```

### 13.4 文档维护

- `PRODUCT.md` 保存范围，`ARCHITECTURE.md` 保存架构。
- `API_SPEC.md` 与实现同步，区分计划接口和已实现接口。
- `DATABASE.md` 说明关系和关键约束，迁移文件是结构演进来源。
- 重要取舍写入 `docs/decisions/`，说明背景、选择和影响。
- README 只承诺已验证能力，写明版本、安装、快速开始和限制。

### 13.5 后续引入 DeepSeek 的方式

当前按双人协作执行，无需等待第三个成员。后续可将边界明确的实现、测试或审查任务交给 DeepSeek：提供 Issue、相关代码、接口契约、禁止修改范围和验收要求；由你运行验证后再集成。公共 API、数据库和状态机的变更先统一，不让多个 AI 分别决定同一契约。

## 14. 风险、安全与发布检查

### 14.1 主要风险与处理

| 风险 | 处理方式 |
| --- | --- |
| Router API 与预期不符 | M0 收集准确版本；M1 前做最小能力验证；用适配器隔离 |
| 指标名和标签差异 | 用实际 Prometheus 数据确认查询，不硬编码未经验证的面板 |
| 多主机实例误判为可重启 | 首版只操作验证过的单服务目标，多节点实例只读 |
| SSH 权限过大或命令注入 | 专用账号、最小权限、单元白名单；参数结构化并严格校验 |
| 任意地址探测形成 SSRF | 限制可访问目标、协议和端口，处理重定向与 DNS 解析边界 |
| 凭据泄露 | 使用秘密引用、日志脱敏、查询不回传凭据 |
| 后台任务重复执行 | 数据库约束、实例锁、幂等键、领取机制和重启恢复核查 |
| 数据损坏或迁移失败 | 迁移前备份、测试升级；恢复时核对版本和数据兼容性 |
| 范围不断扩大 | 按里程碑验收，新增需求入 Backlog |

SSRF 防护应适配私有集群场景：不能简单禁止所有私有地址，也不能因为目标在内网就全部放行。使用部署者配置的可信网络与端点范围，并在实际连接时验证目标。

### 14.2 发布前检查清单

- [ ] M0–M5 的必要验收已经完成，证据对应发布提交。
- [ ] 后端、前端与迁移检查通过。
- [ ] 未认证访问、权限失败、超时、冲突和恢复场景已覆盖。
- [ ] 全新环境按 README 成功部署并完成演示。
- [ ] 默认不提供公开可用的通用密码，管理员初始化方式已说明。
- [ ] 配置示例、日志和打包内容没有真实凭据或敏感地址。
- [ ] 备份、升级、停止和恢复步骤已验证或明确标注限制。
- [ ] LICENSE、第三方依赖说明和必要归属信息齐备。
- [ ] 已知限制包括 Router 适配范围、多节点操作边界和未支持运行时。
- [ ] 发布说明准确，版本标签与发布产物对应同一提交。

### 14.3 建议演示脚本

1. 按 README 启动平台并登录。
2. 登记一个 Router、一台测试主机和一个测试推理实例。
3. 展示真实健康结果和更新时间。
4. 查看至少一个有真实采样数据的监控图表。
5. 对测试实例执行一次受控操作，查看完整任务与审计。
6. 制造一次可恢复故障，确认错误展示和恢复后的状态更新。
7. 重新启动管理平台，确认资源持久化与遗留任务处理正常。
